Running on hardware

Everything else on this site runs on a simulator. This page is about the one step that leaves it: taking a circuit the builder made to a real quantum computer.

Read this first. The hardware package has been tested on simulators only, including simulated copies of IBM devices. It has not been run on a real quantum computer. What has been tested says exactly where the line is.

What a hardware package is

The builder does not send anything to a quantum computer, and it could not: this site is a set of plain pages that holds no account and no key. What it does is write a hardware package, a folder of five small text files that you run yourself, with your own account, when you choose to.

The package holds one problem and the circuit built for it, with its angles already filled in, and a script that:

  1. sends the circuit to the target you pick: a simulator, a simulated copy of an IBM device, or an IBM quantum computer;
  2. reads back the measurements, one answer to the problem per shot;
  3. works out the cost of each answer and reports how close the machine came to the certified optimum.

The third step is what the builder is for. A quantum computer returns bit strings and no verdict. Because the builder has already solved the problem exactly, the script can say how many of the shots were best answers.

Making one

From the page

Run a problem on the builder. The last card, Hardware package, has a button that saves qopt-package.zip. Unpack it. The archive is put together in your browser, and the angles in it are the refined angles of the run on screen.

The page finds angles by simulation, which it does up to 14 variables. For a larger problem the card says so and offers no download.

From the command line

python -m qopt_builder package --preset demo --out demo-package.zip
Problem: Demo graph: weighted MaxCut, 6 nodes (preset demo)
Coupling density: 0.53 (8 of 15 pairs)
Recommendation: exact+qaoa, p = 3
 - n=6 <= 24: an exact classical solve is cheap and certifies the quantum result; recommending exact with QAOA built alongside for comparison.
 - coupling density 0.53 is high: deeper QAOA (p=3) earns its depth on dense graphs.
Certified optimum: -8.000 at x = [0 1 0 0 1 0]
As a cut: weight 8.000
QAOA circuit: 6 qubits, depth 19, 48 gates (6 H, 24 RZZ, 18 RX), 6 free parameters
Angle scan: best expected cost -7.308 over 200 samples (seed 20261110)
Gap to the certified optimum: 0.692
Hardware package written: demo-package.zip (README.txt, problem.json, circuit.qasm, run_on_ibm.py, requirements.txt)
Unpack it and start with README.txt: step 1 runs the circuit on a simulator.

The name after --out decides the form: a name ending in .zip gives an archive, any other name gives a folder. The problem can come from a file of your own, and every option of run works here too. The command line page has the list.

One package, two ways to make it

For the same problem and the same angles, the page and the command line write the same files, byte for byte. The project's tests hold them to that.

Left to themselves they pick different angles, because the page refines the angles it scans and the command line does not. For the demo graph the command line's angles reach an expected cost of -7.308 and the page's reach -7.187. To package the page's angles from the command line, or angles from anywhere else, give them with --gammas and --betas. A problem too large to simulate has to be packaged that way, because neither the page nor the command line can choose angles for it.

What is in it

FileWhat it holds
README.txtThe steps on this page, in short.
problem.jsonThe problem as a matrix, its certified optimum, the recommendation with its reasons, the angles, and the size of the circuit.
circuit.qasmThe circuit, with a measurement of every qubit at the end.
run_on_ibm.pyThe script that runs the circuit and scores the results.
requirements.txtThe Python packages the script needs.

The circuit is written in OpenQASM 2, a plain text format that most quantum software reads. This is how the file for the demo graph starts:

// QAOA circuit made by qopt-builder 0.1.0
// Problem: MaxCut on 6 nodes, 8 edges
// 3 layers, angles filled in; problem.json lists them
// Qubit q[i] stands for variable x_i and is measured into bit c[i]
OPENQASM 2.0;
include "qelib1.inc";
gate rzz(theta) a,b { cx a,b; rz(theta) b; cx a,b; }
qreg q[6];
creg c[6];
h q[0];
h q[1];
h q[2];
h q[3];
h q[4];
h q[5];
// layer 1 of 3: cost
rzz(0.3518925494180574) q[0],q[1];
...

After the opening lines come the gates in order, and at the end a measurement of each qubit. Qubit q[i] stands for variable xi of the problem. The angles are plain numbers by now: this circuit has nothing left to choose.

The answer the results will be measured against is in problem.json:

  "certified_optimum": {
    "cost": -8.0,
    "assignment": [0, 1, 0, 0, 1, 0]
  },

Step 1: a simulator

Start here. It needs no account, and it shows that the package works on your computer before anything else is involved.

cd demo-package
pip install -r requirements.txt
python run_on_ibm.py --simulate

The circuit runs on an ideal simulator, 1024 shots, and the script prints its report. This one is from a run of the package made above:

Step 2: a simulated IBM device

The second step is a rehearsal of the real thing. It still needs no account and uses no quantum time.

python run_on_ibm.py --rehearse

Two things happen that did not happen in step 1.

The circuit is rewritten for a real machine. An IBM device has its own small set of gates, and can apply a two-qubit gate only between qubits that are wired together. Qiskit rewrites the circuit to fit, a step called transpilation, and the result is longer than what the builder made. The report has a line for it, Circuit as sent.

The run has noise. The target is a copy of an IBM device that IBM ships with its software: the layout of a real machine and a record of its error rates, simulated on your computer. The copy used is fake_fez unless you name another, for example --backend fake_torino.

Compare it with step 1. The circuit the builder made has 24 two-qubit gates. The one sent to this device has more than three times as many, and the share of shots that reach the optimum has dropped below what an ideal run gives. That gap is the cost of real hardware, and the reason the builder reports depth and gate counts for every circuit.

IBM's guide to this way of testing points out that the simulated noise covers only part of what a real device does, so a real run is likely to be noisier than its rehearsal.

Step 3: an IBM quantum computer

An account and a key

You need an account on IBM Quantum Platform. IBM's plans page describes a free Open Plan; when this page was written, on 11 November 2026, it allowed up to 10 minutes of quantum time in every 28 days. Check what your plan allows before a run.

The account gives you an API key. Save it on your computer once, from Python:

from qiskit_ibm_runtime import QiskitRuntimeService

QiskitRuntimeService.save_account(token="YOUR-API-KEY")

IBM's instructions for this step, with the options it has, are in Save your login credentials. The key is stored in a file in your home folder. Treat it as a password: do not put it in a script, and do not share it.

The run

python run_on_ibm.py --hardware

The script signs in with the saved key, asks IBM for the least busy device that has enough qubits, rewrites the circuit for that device, and sends one job of 1024 shots. It prints the id of the job, waits for the results, and prints the same report as before.

OptionWhat it does
--backend NAMEUse the device with this name instead of the least busy one.
--shots NRun the circuit N times instead of 1024. More shots use more quantum time.
--job IDDo not run anything. Fetch the results of a job sent earlier, and score them.
--seed SMake the placing of the circuit on the device repeatable.
--out FILEWhere to save the results. Without it they go into the package folder, in a file named after the time and the device.

A job can wait in a queue for a long time. If you stop the script while it waits, the job is not lost: it still runs, and --job with the id that was printed fetches its results later.

There is no report from a real machine on this page, because this package has not been run on one. The rehearsal in step 2 is the nearest thing to a preview.

Reading the report

LineWhat it says
Package, CircuitThe problem and the circuit, as the builder described them.
TargetWhere the circuit ran.
Circuit as sentThe depth and the number of two-qubit gates after the circuit was rewritten for the device. Not shown for the ideal simulator, which runs the circuit as it is.
ShotsHow many times the circuit was run and measured.
Average cost of the shotsThe cost of every measured answer, averaged. Lower is better. It estimates the circuit's expected cost.
Shots at the certified optimumHow many shots gave a best possible answer.
Best assignment foundThe lowest-cost answer among the shots, variable 0 first, and whether it is a certified optimum. For a graph, the next line gives it as the weight of a cut.
Most frequent resultsThe eight answers measured most often, with their costs.

Two of the lines come with a comparison, printed just under them: what an ideal run of the same circuit gives, worked out exactly, and what picking assignments at random gives. They are the two ends to judge a run against. For the demo graph, a random assignment is a best answer 9.4% of the time, and an ideal run of the command line's circuit 53.9% of the time. The comparisons are printed for problems of up to 14 variables.

A problem of more than 24 variables has no certified optimum. Its report says so, and gives the average cost and the best answer found without a verdict on them.

Every run also saves its results as a JSON file, with the count of every answer that was measured.

Other machines

The circuit file is plain OpenQASM 2 and does not depend on IBM. Many makers of quantum computers publish a package that makes their machines usable from Qiskit. With such a package, make its backend object and hand it to the script from Python:

import run_on_ibm

backend = ...    # the machine, from the maker's own Qiskit package
run_on_ibm.run(backend, shots=1024)

The script rewrites the circuit for that machine, runs it through the machine's own run method, and prints the same report. This path has been tested with the generic simulated device that comes with Qiskit, and with no machine of another maker.

What has been tested

Tested, with qiskit 2.6.2, qiskit-ibm-runtime 0.52.0 and qiskit-aer 0.18.2:

  • The circuit file. Qiskit reads it back, and the result is compared gate for gate with the circuit the builder makes.
  • The script on Qiskit's ideal simulator.
  • The script on a generic simulated device with limited connections, which is the path for other machines.
  • The script on simulated copies of two IBM devices, fake_fez and fake_torino, through IBM's own software. This is step 2.
  • The reading of the results. One test problem has a best answer that reads differently backwards, so that a slip in the order of the bits would show. Every target above finds it the right way round.
  • The page and the command line against each other: the same problem and angles must give the same five files, byte for byte, and the same archive when it is stamped with the same time.

Not tested:

  • A run on a real quantum computer.
  • The three things the script asks of IBM's service: signing in with a saved key, getting a device, and fetching an earlier job. They are written to IBM's documentation as it stood in November 2026. With no key saved, the sign-in stops with IBM's own message that no account was found, and that is as far as it has been taken.

If you run a package on hardware, the results file it saves is the evidence. The project would like to hear how it went, through the repository.

Questions people ask

Is my problem sent anywhere when I download a package?

No. The page builds the archive in your browser and hands it to you as a file. Nothing leaves your computer until you run the script with --hardware, and then it goes from your computer to IBM under your account.

Can I use the package without an IBM account?

Yes. Steps 1 and 2 need no account.

Why are the angles fixed in the package?

Finding good angles takes many runs of the circuit, and time on a quantum computer is scarce. The builder finds the angles by simulation, where runs are free, so that one job on the machine is enough. The price is that the builder can only choose angles for circuits small enough to simulate. For a larger problem you bring your own angles.

Qiskit prints bit strings backwards. Does the report?

No. Qiskit writes the last measured bit first. The script turns each result round, so an assignment in the report reads variable 0 first, as it does everywhere else in the builder.

The rehearsal is worse than the simulation. Is something wrong?

No, that is what noise does. The longer the circuit as sent, the further the result falls from the ideal one. A problem with fewer couplings, or fewer layers, gives a shorter circuit: --layers on the command line builds any number you ask for.
